Publishable key ada di dalam aplikasi, sehingga siapa pun yang membongkar APK bisa memakainya untuk memanggil API Supabase. Lalu apa yang mencegah orang iseng membaca catatan milik mahasiswa lain? Jawabannya adalah Row Level Security (RLS).

Konsep: satpam di setiap baris

Bayangkan setiap tabel dijaga seorang satpam. Saat RLS aktif, satpam menolak semua akses, kecuali yang diizinkan secara eksplisit oleh policy. Policy adalah aturan berbentuk kondisi SQL yang dicek untuk setiap baris:

Request: SELECT * FROM notes   (dikirim oleh user dengan id = A)

 baris  | user_id | policy: auth.uid() = user_id | hasil
 -------+---------+------------------------------+---------------
 note 1 |    A    |  A = A  → true               | ✅ dikirim
 note 2 |    B    |  A = B  → false              | ❌ disembunyikan
 note 3 |    A    |  A = A  → true               | ✅ dikirim

Aplikasi tidak perlu menulis .eq('user_id', ...). Database sendiri yang memfilter, sehingga tidak bisa diakali dari sisi aplikasi.

Peran (role) dalam request

RoleKapanNilai auth.uid()
anonRequest dengan publishable key, user belum loginnull
authenticatedUser sudah login (token sesi otomatis dikirim oleh supabase_flutter)id user tersebut (uuid)
service_roleMemakai secret key (khusus server)Melewati RLS sepenuhnya

Contoh 1: data publik yang boleh dibaca siapa saja

-- 1. Aktifkan RLS (setelah ini semua akses ditolak)
alter table public.mata_kuliah enable row level security;

-- 2. Izinkan SELECT untuk semua orang
create policy "Semua orang boleh membaca mata kuliah"
on public.mata_kuliah
for select
to anon, authenticated
using (true);

-- 3. Hanya user yang sudah login boleh menambah
create policy "User login boleh menambah mata kuliah"
on public.mata_kuliah
for insert
to authenticated
with check (true);

Tanpa policy UPDATE dan DELETE, tidak ada seorang pun (dari aplikasi) yang bisa mengubah atau menghapus mata kuliah. Itulah yang kita mau untuk data master.

Contoh 2: data milik pribadi (pola yang paling sering dipakai)

create policy "User melihat catatannya sendiri"
on public.notes
for select
to authenticated
using ( (select auth.uid()) = user_id );

Kita bedah baris per baris:

BarisArti
create policy "User melihat ..."Nama policy, bebas tetapi harus unik per tabel. Tulis nama yang mudah dipahami.
on public.notesTabel yang diatur.
for selectOperasi yang diatur: select, insert, update, delete, atau all.
to authenticatedPolicy hanya berlaku untuk user yang sudah login. User anon langsung ditolak.
using ( ... )Kondisi untuk baris yang sudah ada: baris mana yang boleh dilihat/diubah/dihapus.

(select auth.uid())Dibungkus select agar Postgres cukup menghitungnya sekali per query, bukan sekali per baris. Hasilnya sama tetapi lebih cepat.

using vs with check

Operasiusing (baris lama)with check (baris baru)
SELECT✅ dipakai–
INSERT–✅ dipakai: data yang akan masuk harus memenuhi syarat
UPDATE✅ baris mana yang boleh diubah✅ hasil perubahan harus tetap memenuhi syarat
DELETE✅ dipakai–
 
create policy "User menambah catatannya sendiri"
on public.notes for insert to authenticated
with check ( (select auth.uid()) = user_id );

create policy "User mengubah catatannya sendiri"
on public.notes for update to authenticated
using ( (select auth.uid()) = user_id )        -- hanya baris miliknya
with check ( (select auth.uid()) = user_id );  -- tidak boleh "memindahkan" ke user lain

create policy "User menghapus catatannya sendiri"
on public.notes for delete to authenticated
using ( (select auth.uid()) = user_id );

Apa yang terjadi jika ditolak RLS?

OperasiGejala di Flutter
SELECTTidak error, hanya mengembalikan list kosong []. Ini yang paling sering membingungkan!
INSERTPostgrestException dengan code 42501: new row violates row-level security policy
UPDATE / DELETETidak error, tetapi tidak ada baris yang berubah (0 baris cocok). Jika memakai .select().single(), muncul error karena hasilnya 0 baris.

💡 Melihat dan menguji policy

Buka Authentication → Policies (atau Database → Policies) untuk melihat semua policy per tabel. Di SQL Editor, query dijalankan sebagai admin (postgres) sehingga RLS tidak berlaku. Jadi data yang terlihat di SQL Editor belum tentu terlihat dari aplikasi.

⚠️ Kesalahan umum RLS

  • Lupa enable row level security: tabel terbuka untuk publik. Dashboard menandainya UNRESTRICTED.
  • RLS aktif tetapi lupa membuat policy SELECT: data "hilang", list selalu kosong.
  • Policy using (true) untuk data pribadi: semua user bisa melihat data user lain.
  • Insert tanpa user_id dan tanpa default auth.uid(): user_id bernilai null sehingga with check gagal dan muncul error 42501.
