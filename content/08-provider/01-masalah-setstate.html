Ketika aplikasi Flutter tumbuh besar dan memiliki puluhan halaman, mengandalkan setState() saja akan menimbulkan masalah serius yang disebut Prop Drilling.

Dua jenis state

JenisContohAlat yang cocok
Ephemeral state (state lokal)Tab aktif, isi TextField, checkbox "ingat saya", animasisetState di StatefulWidget
App state (state bersama)User yang login, isi keranjang/KRS, daftar todo, tema gelapState management, misalnya Provider

Aturan praktis: jika data hanya dipakai satu widget, setState sudah cukup. Jika data dipakai oleh beberapa widget yang berjauhan atau beberapa halaman, saatnya memakai Provider.

Masalah Prop Drilling vs Solusi Provider
❌ Tanpa State Management (Prop Drilling)

Jika Widget Anak di tingkat ke-5 membutuhkan data Mahasiswa yang ada di Root, data tersebut harus dioper satu per satu melewati Widget Tingkat 1 -> 2 -> 3 -> 4 -> 5 lewat konstruktor! Widget perantara terpaksa memegang data yang tidak mereka gunakan.

✅ Dengan Provider (Dependency Injection)

Data state diletakkan di atas pohon aplikasi (Root/Scope). Widget manapun di kedalaman berapa pun dapat langsung mengakses data dan mendengarkan perubahannya hanya dengan context.watch() tanpa melalui widget perantara!

Contoh kecil: data dititipkan dari level ke level

// Level 1 punya data
class HomePage extends StatelessWidget {
  final int jumlahKeranjang;
  const HomePage({super.key, required this.jumlahKeranjang});

  @override
  Widget build(BuildContext context) => Header(jumlahKeranjang: jumlahKeranjang);
}

// Level 2 TIDAK memakai data, hanya meneruskan
class Header extends StatelessWidget {
  final int jumlahKeranjang;
  const Header({super.key, required this.jumlahKeranjang});

  @override
  Widget build(BuildContext context) => IkonKeranjang(jumlah: jumlahKeranjang);
}

// Level 3 yang benar-benar butuh data
class IkonKeranjang extends StatelessWidget {
  final int jumlah;
  const IkonKeranjang({super.key, required this.jumlah});

  @override
  Widget build(BuildContext context) => Text('🛒 $jumlah');
}

Header sama sekali tidak memakai jumlahKeranjang, tetapi tetap wajib menerimanya hanya untuk diteruskan ke IkonKeranjang.

Contoh lengkap: katalog dan keranjang tanpa Provider

Jalankan kode ini dan hitung berapa constructor yang menerima data "titipan".

📄 lib/main.dart

// lib/main.dart — salin SELURUH kode ini untuk menggantikan isi lib/main.dart
// Contoh TANPA Provider: perhatikan berapa banyak data yang "dititipkan"
import 'package:flutter/material.dart';

void main() {
  runApp(const MyApp());
}

class MyApp extends StatelessWidget {
  const MyApp({super.key});

  @override
  Widget build(BuildContext context) {
    return MaterialApp(
      debugShowCheckedModeBanner: false,
      theme: ThemeData(colorSchemeSeed: Colors.indigo),
      home: const KatalogPage(),
    );
  }
}

// Pemilik state: semua data keranjang ada di sini
class KatalogPage extends StatefulWidget {
  const KatalogPage({super.key});

  @override
  State<KatalogPage> createState() => _KatalogPageState();
}

class _KatalogPageState extends State<KatalogPage> {
  final List<String> _keranjang = [];

  void _tambah(String matkul) => setState(() => _keranjang.add(matkul));

  @override
  Widget build(BuildContext context) {
    return Scaffold(
      // Titipan 1: jumlah dioper ke AppBarKatalog
      appBar: AppBarKatalog(jumlah: _keranjang.length, isi: _keranjang),
      // Titipan 2: callback dioper ke DaftarMatkul -> ItemMatkul
      body: DaftarMatkul(onTambah: _tambah),
    );
  }
}

class AppBarKatalog extends StatelessWidget implements PreferredSizeWidget {
  final int jumlah;
  final List<String> isi;

  const AppBarKatalog({super.key, required this.jumlah, required this.isi});

  @override
  Size get preferredSize => const Size.fromHeight(kToolbarHeight);

  @override
  Widget build(BuildContext context) {
    return AppBar(
      title: const Text('Katalog (tanpa Provider)'),
      // Titipan 3: data dioper lagi ke TombolKeranjang
      actions: [TombolKeranjang(jumlah: jumlah, isi: isi)],
    );
  }
}

class TombolKeranjang extends StatelessWidget {
  final int jumlah;
  final List<String> isi;

  const TombolKeranjang({super.key, required this.jumlah, required this.isi});

  @override
  Widget build(BuildContext context) {
    return IconButton(
      tooltip: 'Keranjang',
      icon: Badge(label: Text('$jumlah'), child: const Icon(Icons.shopping_cart)),
      onPressed: () {
        // Titipan 4: data dioper ke halaman lain lewat constructor
        Navigator.push(
          context,
          MaterialPageRoute(builder: (_) => KeranjangPage(isi: isi)),
        );
      },
    );
  }
}

class DaftarMatkul extends StatelessWidget {
  final ValueChanged<String> onTambah; // tidak dipakai di sini, hanya diteruskan

  const DaftarMatkul({super.key, required this.onTambah});

  static const matkul = ['Pemrograman Mobile', 'Basis Data', 'Jaringan Komputer'];

  @override
  Widget build(BuildContext context) {
    return ListView(
      children: [
        for (final m in matkul) ItemMatkul(nama: m, onTambah: onTambah),
      ],
    );
  }
}

class ItemMatkul extends StatelessWidget {
  final String nama;
  final ValueChanged<String> onTambah;

  const ItemMatkul({super.key, required this.nama, required this.onTambah});

  @override
  Widget build(BuildContext context) {
    return ListTile(
      title: Text(nama),
      trailing: IconButton(
        tooltip: 'Tambah $nama',
        icon: const Icon(Icons.add_circle_outline),
        onPressed: () => onTambah(nama), // akhirnya dipakai di level terdalam
      ),
    );
  }
}

class KeranjangPage extends StatelessWidget {
  final List<String> isi;

  const KeranjangPage({super.key, required this.isi});

  @override
  Widget build(BuildContext context) {
    return Scaffold(
      appBar: AppBar(title: const Text('Keranjang')),
      // Masalah tambahan: halaman ini tidak bisa MENGHAPUS item
      // tanpa menitipkan callback lagi dari KatalogPage.
      body: ListView(children: [for (final m in isi) ListTile(title: Text(m))]),
    );
  }
}
Katalog: badge menerima jumlah lewat constructor
Keranjang menerima isi lewat constructor

Analisis masalah:

  • AppBarKatalog dan DaftarMatkul hanya menjadi "kurir": menerima data/callback lalu meneruskannya.
  • Menambah fitur hapus di KeranjangPage berarti menambah callback baru yang harus melewati beberapa widget lagi.
  • KeranjangPage menerima salinan referensi list saat dibuka. Jika list berubah, halaman itu tidak tahu harus rebuild karena tidak ada yang memanggil setState di sana.
  • Setiap setState di KatalogPage membangun ulang seluruh halaman, termasuk bagian yang tidak berubah.

ℹ️ Apa yang akan kita pelajari

Di section berikutnya kita membangun solusinya selangkah demi selangkah: ChangeNotifier (tempat state), ChangeNotifierProvider (cara menyediakan state ke pohon widget), lalu watch/read/select (cara membaca state dari widget mana pun).

⚠️ Kesalahan umum

  • Langsung memakai Provider untuk semua state. Isi TextField atau tab aktif tetap lebih sederhana dengan setState.
  • Menyimpan state bersama di variabel global biasa. UI tidak akan otomatis rebuild ketika nilainya berubah.
